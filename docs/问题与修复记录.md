## 一、启动与环境

### 1. `.bat` 双击一闪而过，报 `'NIOENCODING' 不是内部或外部命令`

- **现象**：`start-backend.bat`、`start-frontend.bat`、`stop-servers.bat` 双击后窗口一闪就关，
  或者只报一行莫名其妙的命令错误。
- **根因**：三个脚本是 **LF 行尾**。`cmd.exe` 不支持 LF，会把下一行的字符当成本行命令的一部分，
  于是 `chcp 65001` 变成 `chcp 65001NIOENCODING` 之类的畸形命令。
- **修复**：转成 CRLF（`.gitattributes` 里加 `*.bat text eol=crlf`，防止再次被提交成 LF）。
- **验证**：`file start-backend.bat` 显示 CRLF；双击能正常起服务。

### 2. 端口 8000 被别的项目占用

- **现象**：`start-backend.bat` 窗口一闪就退出，日志里 `address already in use`。
- **根因**：同目录下的 `F:\agent\LedgerCrew` 后端常驻 8000，另有一组 a2a agent 占 8101–8103；
  本项目启动时端口已被占。
- **修复**：停掉占用进程再启本项目。`stop-servers.bat` 只按"本项目命令行特征"匹配进程，
  不会误杀别的项目。
- **注意**：LedgerCrew 有自己的守护进程，停掉后可能被自动拉起，需要的话单独关。

### 3. 改了代码，接口行为却没变（`--reload` 没生效）

- **现象**：明明改了 `qa_agent.py`，接口返回的步骤和参数还是旧的。
- **根因**：残留的 worker 进程启动时间早于文件修改时间，`--reload` 没有触发；
  另外 `--reload-dir app` 只监听 `app` 目录。
- **判断方法**：对比 `python.exe` 的启动时间与文件 `mtime`；worker 比文件旧就是脏进程。
- **修复**：杀掉所有 `uvicorn app.main` 进程后重启，不要指望热重载。

### 4. 后台进程启动失败 / 日志无处可写

- **现象**：`Start-Process` 报"系统找不到指定的文件"，或重定向日志失败。
- **根因**：PowerShell 的 `-FilePath '.\venv\Scripts\python.exe'` 是相对**当前目录**解析的，
  不是相对 `-WorkingDirectory`；`backend\.tmp` 目录根本不存在。
- **修复**：用绝对路径；日志统一写到仓库根的 `.tmp\`。

### 5. DSH 崩溃后 Milvus、MySQL 掉线

- **现象**：会话中断之后，检索报连接失败、`py_compile` 都跑不起来。
- **根因**：DSH 崩溃会带走 Docker Desktop，Milvus 容器随之退出；MySQL 偶发拒绝连接。
- **修复**：启动 `Docker Desktop.exe`，等容器自启（`km_milvus_dev` 等）；确认 `MySQL80` 服务；
  最后重启后端。

## 二、缓存与"命中判定"

### 6. "精确指纹"声称与词序无关，实际有关

- **现象**：`question_fingerprint()` 的注释写"排序拼接，词序无关"，
  但"如何上传文档"和"文档如何上传"指纹不同。
- **根因**：实现是 jieba 分词后**按原序** `" ".join`，词序天然保留；
  真正排序版是 `question_key()`，但没有任何地方调用它（死代码）。
- **修复**：改正注释和文档，**不改行为**——精确层本来就该区分语序，
  同义改写交给第二层 BM25 相似判定兜底。

### 7. 缓存相似阈值靠拍脑袋

- **背景**：相似问句误命中比不命中更糟（答非所问，而且看起来"很确定"）。
- **做法**：三道门同时满足才算命中：
  - 第二层：BM25 检索 top8 → IDF 加权余弦 ≥ `0.85` → softmax 置信 ≥ `0.25`；
    再加数字集合、否定词一致性守卫；
  - 第三层：向量召回 ≥ `0.70` 取 top5 → 交叉编码器逐对打分 ≥ `0.995`。
- **标定**：用 59 对"意思相近但答案不同"的困难问句测出来的，不是估的。

### 8. 测试结果像"没生效"

- **现象**：改了检索/回答逻辑，复测还是老答案。
- **根因**：命中了问答缓存。
- **修复**：测试请求固定带 `use_cache=false`；排查时先看响应里的 `cached` 字段。

## 三、回答质量

### 9. 要关键词，却写成大段文章

- **现象**："给《家庭年度预算与理财计划》生成关键词" → 1460 字、四个大类、还带免责声明。
- **根因**：三件事叠加——系统提示词三条规则都在推长（列表/点明文档/归纳总结）、
  全局 `max_tokens=2048`、问题里的"总结"触发了 agent 长链路。
- **修复**：
  - `detect_format()` 识别 `keywords / short / detailed / default`；
  - 分档 token 预算：`120 / 200 / 1024 / 900`；
  - 关键词与短答**跳过 agent 循环**，单次检索直出；
  - 提示词第一条改成"最高优先级：形式服从请求"。
- **结果**：1460 字 → 72 字；5.86s → 0.70s。

### 10. 每段都对，合起来不像一篇文章

- **现象**：七个分点，每点单看合理，连起来前言不搭后语。
- **根因**：
  - 20 个片段按**分数**排序，同一文档的片段被打散（8 → 12 → 9 → 2）；
  - 分数集中在 0.60–0.66 的噪声带，模型在"哪段更相关"上随机；
  - 提示词没有一致性约束，模型自由发挥。
- **修复**：
  - `order_chunks()`：文档聚簇 + 文档内按 `chunk_index` 升序，上限 **3 篇 × 4 段**；
  - 提示词加【资料一致性】【结构】两条：相邻两段必须有承接，不能各说各的；
  - `score_threshold` 从 `0.0` 提到 `0.35`，低分噪声直接不进上下文。
- **结果**：同一问题的上下文从"10 篇混排"变成"1–3 篇连续窗口"，答案出现明确的承接句。

### 11. 命中的片段是被切断的半句

- **修复**：`_expand_neighbors()` 每篇补最多 3 个相邻片段，标记 `match_type=neighbor`（不相邻补全）。
- **关键点**：补全片段**不参与命中判断**，也不进分数解释，只进上下文。

### 12. 检索不到就硬编 / 拒答不带引用

- **修复**：
  - 低相关闸门 `qa_low_relevance_gate=0.58`、答案下限 `qa_answer_floor=0.40`；
  - 拒答走固定话术，**引用清空**（以前会出现"知识库中没有…[1][2]"）；
  - 生成后自检 `check_answer()`：引用越界 / 重复句 / 超出资料体量 / 跨文档拼接；
  - 命中才触发一次条件重写，重写后长度不足原文 50% 则放弃重写。

### 13. 通用概念题被答成"某个具体项目"

- **现象**："详细讲解一下 agent"返回的全是简历审查 Agent 的实现细节。
- **根因**：检索规划只判断"怎么查"，不判断"问题属于通用概念还是具体项目"。
- **修复**：
  - 规划输出 `scope`：`kb / general / mixed`；
  - `general` 时提示词要求**分两层**——先给学科通识（是什么/怎么搭/常见范式），
    再落到"知识库里的具体实现"，并明确说明知识库只有片段；
  - 规则兜底：命中"是什么/讲解/解释/详细介绍"且不指向具体文档时，强制 `general`
    （实测模型自己判断不稳定，同一问题两次会给出不同层级）。

### 14. 长答案靠拼凑（幻觉）

- **修复**：超体量检查——答案长度 > `max(500, 资料总字数 × 0.8)` 就判定"自行发挥"，
  触发重写。实测 627 字被压到 524 字，删掉的是资料里没有的推断。

## 四、检索质量

### 15. 文件名命中压过内容：0 分片段排最前（本次最典型）

- **现象**：问"人工智能面试宝典中的内容对面试帮助大吗"，返回的参考来源里
  前 4 条全是 `人工智能-简历参考.pdf`，**分数 0.00 却排最前**；
  真正的 `人工智能面试宝典_V6.5.pdf` 反而排在第 5、6 位。
- **根因**（两层叠加）：
  1. **名字匹配给了满额加分**：只要文档名和问题有部分字面重合（"人工智能"），
     就能拿到接近满分，片段本身相不相关不参与判断；
  2. **强命中保底直接置顶**：名字分 ≥ 阈值就无条件塞到结果最前面，不管向量分是多少。
- **修复**：
  - 名字分按**覆盖度打折**：`0.9 × (0.55 + 0.45 × cover)`，
    只覆盖查询一部分的文档拿不到高分；
  - 强命中阈值 `filename_strong_threshold = 0.75`，名额 2 个；
  - 实测：宝典文档名字分 **0.819**（保留保底，排第一）；
    `人工智能-简历参考.pdf` 只有 **0.698**（不再进保底，按真实相关性排）。
- **验证**：同一问题复测，宝典的相关片段排在前列，0 分片段不再置顶。

### 16. 相邻补全的片段被标成"文件名命中"

- **根因**：补全片段继承了被补全片段的 `match_type`，前端标签跟着错。
- **修复**：补全片段标 `neighbor`，前端映射为"相邻补全"；
  分数解释统一用 `vector_score`，不再拿融合分冒充向量分。

### 17. 重复上传的文档占满上下文

- **先做了测量**：`scripts/find_duplicate_docs.py` 用字符 3-gram Jaccard 给 69 篇文档两两算相似度，
  结果最高只有 **0.721**（117/118 两篇 NLP 基础），所谓"同一份笔记 8 个版本"并不存在。
- **修复**：阈值取 `0.6`，只把真正重复的副本聚类，产出 `backend/data/doc_duplicates.json`；
  检索时重复副本分数 × `0.5` 并标 `duplicate_of`。
- **原则**：先测量再定阈值，避免"以为有 8 份重复"就把正常文档也压掉。

### 18. 检索阶段没用交叉编码器

- **修复**：`retrieval_rerank_*`——取 12 个候选、批量 8、`max_length=512`，
  重排失败自动回退向量序。
- **三个实测发现**（决定了它只能在检索里用，不能当拒答判据）：
  1. 模糊问题整体低分（"介绍一下 agent"最高只有 0.10），全低就回退向量序；
  2. 字面重合能骗过它（"今天天气真好"这种例句能拿 0.88）；
  3. 因此**不能**用重排分做"要不要拒答"，拒答仍看向量分。

### 19. 分数阈值 0.0

- **现象**：什么片段都算命中，噪声全进上下文。
- **修复**：`score_threshold = 0.35`。

## 五、延迟

### 20. 寒暄走全链路 21–25 秒

- **根因**：所有输入走同一条最贵的链路（规划 → 检索 → 循环 → 提纲 → 作答），
  "hi"也要 5 次模型往返。
- **修复**：纯规则意图分诊（`_INTENT_RULES`，只认 ≤12 字的整句寒暄）：
  greeting / identity / capability / thanks / bye 直接回固定话术，
  不检索、不生成、不带引用；流式路径同样支持。
- **结果**：21.4s → **0.05s**；"你是谁呀？"25.6s → 0.05s。

### 21. 专业问题 35–40 秒

- **修复组合**：
  - 循环上限 3 → **2 轮**，且某轮没有新增片段就 `early_stop`；
  - HyDE 的假设答案生成与首轮检索**并行**；拆分的子问题**并行**检索；
  - 规划后移到短答短路之后（关键词不再多付一次规划）；
  - 证据早退：`direct` + 命中分 ≥0.72 + 片段 ≥4 + 非对比类 → 跳过工具循环；
  - 操作性提问（怎么用/步骤/教程）强制 `direct`，拆词只会离原文更远。
- **结果**：35.7s → 20.3s；39.5s → 27.7s；对比类 27.4s → 22.3s；关键词 3.4s → 1.5s。

### 22. 自检把正常答案判成"跨文档拼接"

- **现象**："这套知识库系统怎么用"正常引用 3 篇文档，被判跨文档拼接，触发一次全量重写，
  多花 10 秒还把答案改短了。
- **根因**：上下文本来就最多 3 篇，短答案引 3 篇是正常的总览引用。
- **修复**：该检查只在答案 **≥800 字**时触发。
- **结果**：32.1s → 21.6s。

## 六、测试与运维

### 23. 跑评测脚本 CUDA OOM / `0xC0000005`

- **根因**：后端已经占了显存，脚本再起一份 BGE-M3 + reranker（8GB 卡放不下两份）。
- **修复**：先停后端再跑评测脚本；脚本尽量用 `--backend` 模式打接口，不重复加载模型。

### 24. 日志 GBK 乱码

- **现象**：`grep` 中文全部匹配不上，`tail` 出来是 `锟斤拷`。
- **根因**：Windows 控制台默认 GBK 写入。
- **修复**：`iconv -f gbk -t utf-8` 之后再 `grep`；`python -c` 输出含 emoji 时设置
  `PYTHONIOENCODING=utf-8`。

### 25. 两个反复踩到的坑

- **缓存会掩盖改动**：任何"改完没效果"的排查，第一步先 `use_cache=false`。
- **后端是单例**：日志、GPU、Milvus 连接都在一个进程里，重启要干净，不要留下旧 worker。

## 七、沉淀下来的原则

1. **阈值来自标定，不来自直觉。** 缓存的 0.85/0.995 用 59 对困难问句标出来；
   重复文档的 0.6 是先测了 69 篇的分布才敢定。
2. **模型判断不可靠的地方用规则兜底。** `scope`、意图、操作性提问、早退条件，
   都是"模型给建议 + 规则做决定"。
3. **贵的步骤只在真正需要时做。** 寒暄不检索、关键词不进循环、证据够就早退、
   短答不跑提纲。
4. **每个"命中"都要能解释。** 前端标出"文件名命中 / 文件名+语义 / 相邻补全 / 阅读原文"，
   并区分融合分与向量分——用户看到 0 分排第一时，能立刻定位到是哪一环放大的。
5. **改完必须回归。** 固定问题集（9 条问答 + 缓存 28 对）每次改检索/提示词都跑一遍，
   避免"修一个坏一个"。
